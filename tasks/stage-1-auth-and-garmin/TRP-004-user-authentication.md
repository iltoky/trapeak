# TRP-004 — Реализовать авторизацию пользователя TRAPEAK

## Description

Реализовать регистрацию и вход по `email + password`, выход, получение текущего пользователя, восстановление пароля и защиту приватных страниц.

Использовать готовое, поддерживаемое auth/session-решение, выбранное в ADR TRP-001. Не писать собственную криптографию, password hashing или session framework.

## Scope MVP

- регистрация по email и паролю;
- вход по email и паролю;
- выход из текущей сессии;
- получение текущего пользователя;
- защита приватных routes;
- запрос восстановления пароля;
- установка нового пароля по одноразовой ограниченной по времени ссылке;
- подтверждение email, если выбранное в TRP-001 решение позволяет добавить его без существенного усложнения; требование для production должно быть явно зафиксировано в ADR.

Social login, magic link и MFA не входят в задачу.

## Functional Requirements

- Email нормализуется до сравнения и хранится уникально.
- Политика пароля описана в UI и проверяется на сервере.
- Пароль перед записью хешируется поддерживаемой библиотекой и никогда не сохраняется в открытом виде.
- Login и password reset возвращают нейтральные ответы, не позволяющие определить наличие email в системе.
- Reset token одноразовый, ограничен по времени и не хранится в БД в открытом виде.
- После успешной смены пароля существующие пользовательские сессии инвалидируются либо ADR явно обосновывает другое безопасное поведение.
- Повторная регистрация существующего email обрабатывается предсказуемо без раскрытия лишних данных.
- На login, registration и password reset действует rate limiting.
- Пароли, password hashes, reset tokens, session tokens, cookies и auth headers не попадают в логи.

## Acceptance Criteria

- Новый пользователь может зарегистрироваться по email и паролю.
- Зарегистрированный пользователь может войти и выйти.
- Сессия сохраняется после обновления страницы.
- Неавторизованный пользователь не открывает приватный route.
- Пользователь не получает данные другого пользователя.
- Повторный email не создаёт второго пользователя.
- Пользователь может запросить восстановление и установить новый пароль по валидной ссылке.
- Просроченная или повторно использованная reset-ссылка отклоняется.
- Старый пароль не работает после успешной смены.
- Cookies настроены безопасно для production.
- Критические сценарии покрыты integration tests.

## Release Actions

- Добавить `AUTH_SECRET` и остальные secrets выбранного auth-решения в окружение.
- Настроить почтовый сервис и адрес отправителя для password reset и, при использовании, подтверждения email.
- Настроить production URL на домене `trapeak.com`.
- Убедиться, что в Git нет secrets и реальных учётных данных.

## Testing Recommendations

Проверить:

- session fixation и logout;
- истечение сессии;
- generic error messages;
- rate limiting и защиту от перебора;
- повторный email;
- параллельное и повторное использование reset token;
- инвалидацию сессий после смены пароля;
- отсутствие чувствительных auth-данных в логах.

## QA e2e tests

1. Регистрация нового пользователя.
2. Вход и открытие приватной страницы.
3. Неверный пароль возвращает нейтральную ошибку.
4. Logout закрывает доступ.
5. Неавторизованный запрос перенаправляется на login.
6. Сессия одного пользователя не даёт доступ к данным другого.
7. Запрос восстановления для существующего и несуществующего email выглядит одинаково.
8. Установка нового пароля по валидной ссылке.
9. Просроченная и повторно использованная reset-ссылка отклоняется.
10. Старый пароль и старые сессии не работают после смены пароля согласно ADR.
