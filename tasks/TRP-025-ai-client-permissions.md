# TRP-025 — Разрешения для подключённых AI

Статус: **Planned; security design required**

## Description

Дать владельцу возможность отдельно настраивать доступ каждого подключённого OAuth-клиента / AI к данным TRAPEAK. В первом срезе используются не роли, а явная матрица:

- категории: `training`, `nutrition`, `health`;
- операции: `read`, `write`;
- удаление — отдельное разрешение, выключенное по умолчанию и не входящее в обычный `write`.

Пример: ChatGPT получает `training + nutrition` с чтением и записью, второй AI — только чтение `training`, а AI для врача — только чтение `health`.

Для владельца действует policy конкретного AI. Если AI работает с делегированным доступом специалиста, эффективные права вычисляются сервером как пересечение:

`AI client policy ∩ human grant ∩ разрешённые сервером операции`

AI никогда не может расширить human grant или получить данные только на основании текста промпта.

## Acceptance Criteria

- В dashboard отображается список подключённых AI с понятным названием, `clientId`, состоянием и действием revoke.
- Для каждого AI владелец явно выбирает категории и `read/write`; `health` требует отдельного consent.
- Проверка выполняется на сервере для каждого MCP tool по `clientId`, категории и операции.
- Новый AI не получает категории данных до явного выбора владельца; стратегия миграции уже подключённых клиентов согласована до разработки.
- `write` разрешает создание и обновление только по явному запросу пользователя. Удаление остаётся отдельным разрешением и подтверждением.
- При delegated access права AI пересекаются с активным grant получателя; revoke или expiry human grant немедленно закрывает доступ.
- Отзыв AI-клиента или изменение его policy начинает действовать немедленно для новых запросов.
- Audit фиксирует владельца, получателя при delegated flow, `clientId`, категорию, операцию, результат проверки и время.
- UI настроек AI не смешивается с выдачей доступа человеку по email.
- Threat model покрывает подмену `clientId`, confused deputy, устаревшие токены, обход через универсальный tool, повышение `read` до `write` и утечку `health`.

## Release Actions

1. Утвердить threat model, модель хранения client policies и поведение существующих подключений.
2. Добавить миграцию и серверный policy enforcement для всех MCP tools.
3. Добавить dashboard управления подключёнными AI, consent и revoke.
4. Обновить OAuth/MCP-инструкции и описание privacy model.
5. Выполнить authorization matrix tests, authenticated e2e и контролируемый production rollout.

## Testing Recommendations

- Покрыть unit/integration-тестами каждую пару `категория × операция` и default deny.
- Проверить одинаковую policy enforcement для owner и delegated flows.
- Проверить, что универсальные и агрегирующие tools не возвращают поля закрытых категорий.
- Проверить немедленный эффект изменения policy, revoke AI и revoke/expiry human grant.
- Проверить audit как для разрешённых, так и для отклонённых запросов.

## QA e2e

1. Подключить два AI к одному владельцу и выдать им разные категории и операции.
2. Убедиться, что AI с `training + nutrition: read/write` может читать и добавлять разрешённые данные, но не видит `health`.
3. Убедиться, что AI с `training: read` не может записывать данные или читать другие категории.
4. Открыть специалисту только `training`, затем проверить, что его AI с более широкой client policy всё равно видит только `training` и только read-only данные.
5. Отозвать client policy и human grant по очереди; каждый следующий запрос должен быть отклонён и записан в audit.
